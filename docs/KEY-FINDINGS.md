# omaframe 关键结论速查（后期回顾用）

> 更新时间：2026-09-28 · 对应提交 `572dbd6`
> 源码 `~/Omaframe`，本文件只记录**已验证有效**的结论和踩过的坑，细节见 `docs/PLAN.md`。

> 需求清单与禁忌速查见 [`REQUIREMENTS.md`](REQUIREMENTS.md)；本文只放技术根因与推导。

## 一、最终架构（已实测 1:1 精确）

```
layer surface = 整个显示器（1536×864），尺寸恒定、永不重建
└── 相框矩形 = 配置 window.x/y（相框左上角）+ fit(PNG比例, 目标盒)
    ├── 媒体纹理（照片/视频帧）
    ├── PNG 相框（比素材大 3%，居中）
    └── 悬停控制层（底部中央 ▶/⏸；左/右半区点击切上/下一项）
```

**为什么 surface 必须铺满显示器**（本项目最关键的一条）：
拖动/缩放时指针会移出"相框矩形"。如果 surface 只有相框那么大，
指针一移出 → GTK 停止派发事件 → 位移冻结在离开点（"只移动一部分距离"），
而靠轮询补偿又会带来"慢半拍 + 拖尾"。铺满整屏后指针**永远不可能离开控件**，事件全程连续。

## 二、拖动/缩放：四条铁律

1. **事件驱动，禁止轮询**：每个 `drag-update` 立即应用（`d.acc = (dx,dy)`，GTK 的 delta 是**相对按下点的绝对位移**）。
   早期用 16ms 计时器轮询指针位置 → 松手时最后一段常没被读到，且整体半拍延迟。
2. **拖动中输入区域放宽到整屏**（`view.set_dragging(true)`）；平时只覆盖相框矩形，留白点击穿透桌面。
   缩放时指针必然离开相框，不放宽手势会立刻断掉。
3. **拖动/缩放期间绝不碰 layer surface**（不 `set_margin`、不改尺寸）——每帧 configure 往返是卡顿主因。
   移动 = 绘制偏移；缩放 = 预览虚线框；松手才应用一次。
4. **窗口底色必须显式透明**（CSS `window/.background`）。不透明时偏移后原位置会留**黑色残影**；
   而且相框 PNG 的透明处会露出主题深色（用户报的"最外层黑色"）。

**实测（uinput 相对位移 + 按住，等效真鼠标）**
| 场景 | 光标 | 相框 | 误差 |
|---|---|---|---|
| 移动 | Δ(231,134) | Δ(231,135) | (0,1) ✓ |
| 缩放 | +200,+120 | 上限 254×143→455×255 | 比例 1.776→1.784 ✓ |

## 三、已确认的根因速查（按症状查）

| 症状 | 真根因 | 修法 |
|---|---|---|
| 点击/按住出现"放大黑屏" | 拖动中放大 widget → layer surface 重建 → 合成器画成不透明黑块 | 固定画布，绝不在拖动中改 surface 尺寸 |
| 拖动只走一段 / 慢半拍 / 拖尾 | 指针移出控件致事件中断 + 计时器轮询 | surface 铺满显示器 + 事件驱动 |
| 相框"外层一块黑" | ① PNG 四角不透明 ② **窗口透明 CSS 根本没注册成功** | 遮罩 = 外圈圆角 − 中心圆角；CSS 加到 `FrameWindow::new` 并挂解析错误日志 |
| 切素材时窗口"退出又打开" | 换素材改 surface 尺寸 → 重建 | 画布恒定，媒体只改绘制 |
| 视频加载前黑闪 | 切视频时先清纹理，首帧 0.2~0.5s 内 surface 无内容 | 保留上一项画面，首帧到达再替换 |
| 托盘图标点击无反应 | quickshell 发 `Activate(ii)`（两个参数），只声明一个 → GDBus 以 InvalidArgs 拒绝 | XML 声明 `x,y` 两个 int；删掉指向空对象的 `Menu` 属性 |
| **崩了**（SIGABRT）| `GObject::set_property` 写入**不存在的属性**（`propagate-natural-width` 不是 `AdwPreferencesPage` 的属性）→ glib 直接 panic→abort | 删掉该行；凡是设属性一律先确认目标对象真的有这个属性 |
| 设置页窗口缩不小 | `set_size_request()` 设的是**最小**尺寸，误当目标尺寸用（400x560）→ 窗口被撑死 | 面板尺寸用 `set_default_size`；`set_size_request` 只当宽度下限 |
| 设置页 Esc 关不掉 | `EventControllerKey` 默认在 bubble 阶段，焦点在 Entry 里时按键先被输入框消费 | 改用 **capture 阶段**的 `EventControllerKey`（+bubble 兜底），焦点在输入框也能关窗 |
| 位置停靠除居中外都偏 | 用**画布**尺寸贴靠，而相框在画布内居中 | 按**相框矩形**贴靠：`画布位置 = 期望相框位置 − 相框偏移` |
| 改边距/位置后重启丢失 | `apply_anchor` 只 `edit()` 没 `commit()` | 末尾补 `commit()` |
| 调试浮层开关无效 | 运行时没真增删 HUD | `set_debug()` 运行时创建/移除标签 |

## 三点五、相框遮罩算法（异形相框的正确解法）

- **症状**：PNG 相框是**异形/不规则外轮廓**（斜切角、圆角过大、波浪边）时，媒体矩形会从
  PNG 的透明缺口**漏出矩形边角**，非常难看。
- **错误做法**：只裁一个矩形（内孔包围盒）→ 圆孔的四个角仍会漏。
- **正确算法**（`frame.rs::build_hole_mask`）：
  1. 扫描 alpha，**从四边洪泛**透明像素：能到达的 = 外部，到不了的 = 内孔
     （"透明像素包围盒"分不清「圆孔四角」和「外轮廓缺口」，必须洪泛）
  2. 允许显示媒体的区域 = 非外部透明（相框本体 ∪ 内孔）；真正要擦掉的只有外轮廓之外的缺口
  3. 遮罩整体 3×3 盒式模糊 → 外轮廓边缘 1px 羽化（半透明渐变观感）
  4. 运行时 cairo `DestOut` 用遮罩擦媒体，再把相框 PNG 叠在最上层
  5. 没有内孔（纯装饰框）→ 自动退回原叠图模式
- **实测**（用户的 floral frame `fower.png`，2688×1515，薄边框+四角花，只有 23% 像素不透明）：
  框外像素 rgb(109,164,85) 与远处壁纸 rgb(109,164,81) 一致 → 相框外**无任何媒体** ✓
- **坑**：遮罩是**灰度图**（无 alpha），读像素必须按 **1 字节/像素**；
  用 `n_channels()` 去乘会把行内位置算错，内孔边界整体偏移（曾导致 40px 的孔变成 14px）。
- 已撤销：`FRAME_GROWTH`(相框×1.03) 与 `media_scale`(媒体×0.96) 两个"百分比缩放" ——
  让位交给遮罩；`display.media_scale` 字段已**彻底删除**（旧配置里那行会被 serde 忽略，不影响加载）。
- **三个必须记住的坑（都真踩过，症状都是"媒体从相框漏出/露边"）**：
  1. **`DestOut` 必须先 `translate` 到相框矩形**：遮罩按"相框矩形尺寸"生成，
     但 cairo 上下文原点是 surface (0,0)。少了平移就擦错区域 → 媒体整片漏在相框外。
  2. **`ALPHA_CUT` 取 160（约 0.63）而不是 24**：真实相框外沿常有**半透明羽化带**
     （alpha 0.13~1.0 渐变）。若把它当"透明内孔"，媒体会一路画到相框外沿，
     羽化带后面透出一条图片（用户报的"图片上边缘会露出相框"）。
  3. **媒体绘制矩形要比内孔略微内缩 1px**（`MASK_INSET`）：让媒体硬边藏进不透明环内，
     不能外扩（外扩必从羽化带透出）。

## 三点五点一、内孔可用范围 = 整片透明区域的**最大宽高**

- 用户明确要求：素材宽高要**最大化填充**内孔，所以内孔范围取
  **整片透明区域的外接 min/max**（`build_hole_mask` 里的 `hx0/hy0/hx1/hy1`）。
- **不要再改成"逐行最宽段的中位数/密集核心"** —— 那是为避让顶部报纸角装饰想出来的保守算法，
  会把可用区算小：木纹上沿从真实的 `0.008` 被压到 `0.135`，素材白小一圈；
  竖图时相框还会缩成 280×153（横图 668×364）→ **换张图相框就跳变**。
  不规则形状/装饰让**遮罩**去裁，素材该占满最大范围（花环的花朵自然会压在照片上，观感正常）。

## 三点六、视频清晰度（易回退的一个坑）

- **症状**：视频在相框里发糊（图片清晰）。
- **根因**：ffmpeg 管线只按**逻辑像素**出帧（如 358×200），
  而显示器有缩放（本机 1.25×，GDK `scale_factor()` 报 2）→ 合成器把帧再放大 → 模糊。
- **修法**：`show_video` 的目标框 = `上限盒 × (1+grow) × monitor_scale`（与图片 `decode_box` 一致），
  实测 358×200 → **713×401**；缩放器从默认/bilinear 换成 **lanczos**（小窗缩小画质差别明显）。

## 三点七、内置相框库 + 相框样式 + 显示比

- 相框库在**程序目录 `frame/`**（原 `~/frame` 已移入，8 个中文名 PNG）。
  `config::frame_dir()` 解析顺序：`<exe同级>/frame` → `<exe上级>/frame` → 源码目录 `frame/`；
  `list_frame_styles()` 读取其中所有 `.png`（按名称排序）作为设置页下拉选项。
- 配置：`frame.style = "横-木纹.png"`（**文件名**，不是绝对路径；相框库已改名为 横-*/竖-*）。
  ~~`frame.zoom` = 0..100~~ → **已移除**：`FrameConfig` 里没有 `zoom` 字段，
  `player.rs::apply_zoom()` 硬编码 `set_media_zoom(1.0)`（素材恒 100% 铺满内孔）。
  旧的 `frame.path` 会在 `Config::sanitize()` 里**自动迁移**成 `style`
  （`Loaded.migrated` 标记 → boot 立即落盘，不等退出）。
- **尺寸关系（相框宽高自适应：比素材大 grow%，默认 3）**：
  1. 内孔范围 `draw` = 整片透明区域的最大外接范围（相对 PNG 的 0..1 比例，见 3.5.1）
  2. 素材尺寸 = `fit(素材比例, 上限盒)`；目标盒 = **素材 × (1+grow%)**（默认 3%）
  3. 相框尺寸 = `geometry::frame_size_for_box(draw, PNG比例, 目标盒)`
     约束：`fw ≤ 目标盒.w/draw.w`、`fh ≤ 目标盒.h/draw.h`、**`fw/fh = PNG 自身比例`**（不拉伸）
  3. 素材绘制矩形 = `geometry::media_rect_in_hole(相框矩形, draw, 显示比)`
     → 正好铺满内孔最大范围，再按显示比以该区域中心缩放
  4. 纹理按 **cover** 画进绘制矩形：素材比例与内孔比例不同时做**最小裁切**（真实相框的"填充"做法）
- **实测（上限 490×320、grow 3%、木纹）**：内孔最大范围 = 素材(490×276) × 1.03 → 素材 **505×281**，
  相框外框 **610×332**（外框比素材大是因为 PNG 自身边框厚）。
  约束更紧的一边精确等于"素材 × 1.03"，另一边不超过它（相框比例恒等于 PNG 比例）。
  各相框内孔最大范围（相对 PNG）：木纹 0.07~0.898 × 0.008~0.854；花环 0.051~0.969 × 0.05~0.937；
  猫线 0.061~0.933 × 0.251~0.91（内孔本身就是扁的 → 素材自然被裁成扁幅面）。
- **图片/视频清晰度（又一个易回退的坑）**：解码尺寸必须 **≥ 实际绘制矩形**。
  历史上 `decode_box`/视频 `set_box` 乘过一个"媒体内缩 0.96"的系数，导致解码比绘制小 4%，
  合成器再放大回来 → 图片/视频发糊（用户报的"加载图片模糊"）。该字段已删除，别再引入类似系数。
  正确做法：`上限盒 × (1+grow%) × monitor_scale() × 1.06`（1.06 是 cover 裁切余量）。
- 显示比实现：`media_rect_in_hole(...)` —— 以**内孔可用区中心**为基准缩放
  （不规则内孔的中心未必是相框中心，所以不能再按相框中心放）。
- 换样式/改显示比都是**立即生效**：`player.load_frame()` + `player.apply_zoom()`。

## 四、语义与配置约定

- `display.max_width/max_height` = **素材绘制矩形的上限**（相框会随内孔比例变大，
  所以相框外框**可以大于**这两个值；420 行夹在整屏尺寸内）。
- `window.x/y` = **相框左上角**的屏幕坐标（不是 layer 边距；layer 边距恒为 0）。
  `geometry()` 里必须**直接用 x/y 当相框左上角** —— 拖动、停靠、输入区域、可见性判定全都这么假设；
  曾经把 x/y 当"素材左上角"再居中相框，相框一大就整体偏出屏幕（日志 `输入区域 → …+0+112`）。
- 右下角缩放拖动改的是**上限盒**（`geometry::resize_target_box`）：盒宽增量 = 鼠标位移 / k，
  `k = 当前素材宽 / 当前盒宽` → 手感依旧"鼠标走多少照片变多少"；松手才写配置。
- `display.media_scale`：**已删除**（旧配置里残留该行会被忽略）。
- `frame.desktop_enabled` = 默认 true；关掉后相框从桌面隐藏（媒体继续解码，设置/托盘不受影响）。
- `frame.style` = 内置相框库里的 PNG 文件名；
  ~~`frame.zoom` = 素材显示比~~ → **已移除**，见 3.7；
  `frame.grow_percent` = 相框比素材大多少（默认 5）；`frame.debug_hud` = 调试浮层（持久化）。
- **所有设置即时落盘**：设置页每行都走 `AppState::update()`（内部 = `edit` + `commit`），
  拖动/贴靠在松手时 `commit`；重启后全部自动恢复（含调试浮层）。
- 相框矩形 == 媒体矩形；`frame.enabled` 关闭时纯展示媒体。
- 输入区域平时 = 相框矩形（**相框外点击穿透桌面**，不挡操作）；拖动中 = 整屏。
- 拖拽判定阈值 2px（`gtk-dnd-drag-threshold`，默认 8px 太迟钝）。

## 五、环境事实（本机实测，别再重复踩）

- GStreamer **只有 base 插件**（无 h264/hevc/vp8/theora/matroska）→ 视频走**系统 ffmpeg**（`owe` 同款后端），零新增依赖。
- mpv 0.41 **无 `--window-layer`** → 不能像动态壁纸那样开层表面。
- Hyprland 0.56：dispatch 是 Lua 语法（`hl.dsp.focus({workspace=3})`）；事件 socket 是 `.socket2.sock`（旧版 `.sock2`）；
  事件负载是 CSV 且**不含几何**（几何要用 `hyprctl -j clients`）。
- 本机 `reserved: 23 0 0 0`，layer surface 原点 ≈ 屏幕 (0,22)：屏幕坐标与 surface 坐标差 22px（y）。
- GTK 4.22 已把 GDK 并入 `libgtk-4`（无 `gdk-4.0.pc`）；glib 0.22 **没有 `clone!` 宏**，用 `glib::WeakRef`/`Rc<Cell<..>>`。
- 托盘、遮挡暂停、ffmpeg 缺失都会**降级不报错**；全程不写 hypr/omarchy 配置、不需要 root。

## 三点八、设置面板（弹出式，2026-09-29）

需求：点状态栏图标弹出设置页；**点面板外 / Esc / 失去焦点**都自动隐藏（Omarchy 插件那种手感），
且面板里的下拉、开关必须能用鼠标正常操作。

**最终形态（`settings.rs`）—— 只有一个窗口**：
- 面板窗口铺满"顶栏以下"（`Layer::Overlay`、锚 `Top|Left`、`set_size_request(显示器尺寸)`、
  `KeyboardMode::Exclusive`），左上锚定 + **显式尺寸**（不做四边拉伸）。
- 面板卡片（固定宽 360 + 圆角 popover 背景 + 内部 ScrolledWindow）在窗口内对齐右上角。
- **点卡片外 → 收起**：根容器 capture 阶段 `GestureClick`，用 `shell.compute_bounds()` 判断
  落点是否在卡片内 → 在卡片外才 `hide()`。窗口铺满屏幕 → 点击被本窗口吞掉（真弹窗语义），
  且顶栏（y<22）不在窗口内 → 状态栏图标仍可点（再点一次也能关）。
- Esc → `close_request` → `hide()`；`omaframe settings` / 托盘图标 → `toggle()`。
- 隐藏即**销毁**窗口 → 下次打开必是最新配置（拖动改过的宽高立刻反映）。
- 另一个窗口**真的**拿到焦点（Hyprland `activewindow(v2)` 事件，按负载去重）→ 也收起。

**踩过的坑（都很隐蔽，别重犯）**：
1. **四边锚定的 layer surface 收不到鼠标事件**：合成器把这种 surface 拉伸，但 GTK 侧收不到
   configure，控件分配停在最小值 → 无输入。（`hyprctl layers` 看得到、`a: 1`、输入区域也显式设了
   —— 都没用。）同层同尺寸的**面板窗口**能收点击，区别就在"是否显式尺寸/非拉伸"。
   → 结论：别用第二个"透明遮罩表面"做点外关闭，直接让面板窗口铺满屏幕。
2. **不能用 `is_active_notify` 做"失去焦点就隐藏"**：面板里的下拉（AdwComboRow）打开时是 GTK 弹窗，
   会让 toplevel 的 `is_active` 变 false → "点下拉面板立刻消失"（用户报的 bug）。
3. **Hyprland 焦点事件只认 `activewindow(v2)`**：把 `workspace` 也算进来会误关面板
   （点下拉时也会补发 workspace 事件）。另外事件按负载去重（同一窗口补发的事件不带变化）。
4. **全透明的 layer surface 会被当成不可见**（`hyprctl layers` 里 `a: 0`）；现在面板根容器有一层
   很淡的压暗（rgba 0.08），既是模态观感也保证 alpha>0。
5. 面板内容比屏幕高 → 必须自己包一层 `ScrolledWindow`（`propagate_natural_height(false)`），
   AdwPreferencesPage 单用会直接把高度报给窗口、被裁掉且滚不动。

**托盘 SNI 顺带修的一个真 bug**：`ToolTip` 的签名必须是 `(sa(iiay)ss)`（图标名、图标像素数组、
标题、描述）。之前写成 `(("omaframe",), Vec<(i32,i32,i32,i32)>, tooltip)` —— 少一个字段、
内层类型也不对，quickshell 每 30 秒报一次 DBus 签名错误刷日志。现在用
`("omaframe", Vec::<(i32,i32,Vec<u8>)>::new(), "桌面相框", tooltip)`。

## 三点九、控制层（播放/暂停按钮）显隐的两个坑（2026-09-29）

用户报：播放/暂停按钮应"指针进窗口才显示、移出就隐藏"，实际是**点过暂停后按钮一直挂着**。

**根因 1（主因）：控制层的"重绘钩子"从来没注册。**
`Controls` 的淡入淡出是自绘的（`progress` 0→1），GTK 不会因为 Cell 变化自动重画，
所以它内部有 `redraw` 回调 —— 但 `MediaView::new()` 里**没有调用 `set_redraw_hook()`**，
于是 `request_redraw()` 是空操作：动画只在"别的重绘顺便带上"时才看得见
（指针移动本身会 `queue_draw`），**光标停下后最后一帧（progress=0）永远刷不出来** →
按钮留在屏幕上。修法：构造时把 `view.queue_draw` 注册进去（用 `WeakRef` 避免循环引用）。
→ 教训：自绘 + 动画的组件，一定确认"请求重绘"这条链路真的接上了（这类 bug 表现为
"动画看起来在工作，但最后一个状态刷不出来"）。

**根因 2（鲁棒性）：不能只靠 enter/leave 判断 hover。**
按下/拖动时输入区域会临时扩到整屏（为了拖出相框也不丢事件），此时指针移出相框
**不会再收到 leave** → hover 冻结在"显示"。修法：每次 motion 都按**指针实际位置**判断
（`ControlLayout::hit()` 落在框外返回 `None`，正好当判据）→ `set_hover(zone != None)`。

## 三十、layer-shell 面板里开对话框：点"打开目录"闪退（2026-09-30）

**现象**：设置面板点"媒体 → 打开"选目录，程序立刻闪退；`coredumpctl` **没有**新记录，
日志最后一行是 `Gdk-Message: Lost connection to Wayland compositor`，
Hyprland 侧报 `error in client communication (pid …)`。

**根因**：`gtk::FileDialog::open(parent, …)` 把**设置面板**当对话框的 transient parent，
而面板是 **layer-shell surface**（不是 `xdg_toplevel`）→ 触发 Wayland 协议错误 →
**合成器直接踢掉客户端**（所以没有 coredump、不是 Rust 侧的 panic）。
另外面板在 **Overlay 层且盖满屏幕**，普通 toplevel 的对话框会被它整个挡住。

**修法**（`settings.rs` 的目录选择按钮）：
1. `dialog.open(None::<&gtk::Window>, …)` —— **不传父窗口**（避免给 layer surface 设 parent）。
2. 点按钮先 `hide(panel)`，对话框关闭（选中或取消）后再 `show(panel)`。
3. 顺带加"刚显示 500ms 宽限期"（`within_show_grace`）：从对话框关掉回来时，
   焦点正好切回原窗口，不该被 `activewindow` 事件当成"失去焦点"立刻把面板又关掉。

**同类推广**：任何 `xdg_toplevel` 相关的父子/瞬态关系都不能挂到 layer-shell surface 上；
需要模态/父窗口时，要么让对话框独立开，要么先把 layer surface 藏起来。

**验证**：点"打开" → 对话框正常弹出且可见、程序不退出；点"取消" → 对话框关闭、
面板回来并保持（不被焦点事件误关）、配置未被改动。

## 三十一、智能自适应 PNG 相框引擎（2026-09-30）

目标：**任意透明 PNG 相框 × 任意比例图片/视频 → 自动适配**，不需要人工配置、不为某张 PNG 写死坐标。

### 模块与数据流

```text
PNG ──降采样(≤512px)──▶ Alpha 二值化 ──边界洪泛──▶ 外部透明区
                                │
                   内部透明区 = 未被外部连通
                                │
                   最大连通块 = 真实内孔（排除零散小洞）
                                │
                   形态学腐蚀（安全边距，避开羽化/装饰毛刺）
                                │
                   最大内接矩形（直方图 + 单调栈, O(W×H)）
                                │
            映射回原分辨率 ──▶ FrameModel ──▶ 磁盘缓存（path+mtime+size+版本+阈值）
```

- `src/frame_model.rs`（新）：全部分析逻辑 + `FrameModel` + 运行时遮罩 + 缓存 + 单测
- `src/geometry.rs`：`RectI`、`layout_adaptive()`（九宫格布局）、`slices_src()`
- `src/frame.rs`：`FrameSlices`（相框 9 片 + 遮罩 9 片，**按原始分辨率**保存，绘制时 cairo 缩放）
- `src/window/media_view.rs`：九宫格绘制 + 抗锯齿遮罩 + Debug Overlay（`PHOTO_FRAME_DEBUG_OVERLAY=1`）
- `src/config.rs`：`frame.fit = smart | cover`

### FrameModel 关键字段（**两个概念不要合并**）

| 字段 | 含义 | 用途 |
|---|---|---|
| `hole` | 内部透明区**包围盒**（最大连通块） | **九宫格中心片 + 素材铺满的内孔**；相框拉伸以它为基准 |
| `safe` | 内孔腐蚀安全边距后的**最大内接矩形** | 质量评估/诊断；保证"没有装饰混进来"，但不作为拉伸基准 |
| `canvas` / `analysis` | 原图尺寸 / 分析尺寸 | 坐标映射 |
| `alpha_threshold` | 透明判定阈值（默认 8） | 缓存键的一部分 |
| 运行时 `mask` | 抗锯齿遮罩（见下） | 最终"底图绝不能穿过相框" |

### 九宫格自适应（相框可横可竖、四角不变形）

- 源切片：以 `hole` 把 PNG 切成 9 片（四角 = 内容区到画布的边距，四边取中间段，中心 = 内孔）。
- 目标切片：设统一缩放 `k = max(内容宽/内孔宽, 内容高/内孔高) × (1+grow)`，
  四角 = 源尺寸 × k（**宽高同比缩放 → 绝不变形**），四边只沿一个方向拉伸。
- 相框外框 = 内容 + k×(左右/上下边框) → **素材是竖的，相框就自动变竖**（以前死守 PNG 比例，
  只能把竖图裁成横条）。
- 不变量（有单测）：`media == dst[CENTER]`、九片无缝无重叠、四角宽高比与源一致。
  → 素材 contain 进中心片正好铺满，**不会露一圈桌面**。

### 抗锯齿遮罩（0~255，保留半透明）

```text
框外（内孔 bbox 之外且 alpha ≤ 阈值） → 255  彻底擦掉，媒体绝不漏出
相框本体 / 羽化带                     → 相框真实 alpha（半擦）
内孔                                 → 0    媒体完整显示
```
用 cairo `DestOut`（`dst *= 1 - mask_alpha`）逐片作用到媒体上，
所以相框的发光/阴影/羽化边缘都是自然过渡，**没有锯齿、没有白边/黑边**。

### 失败降级（不崩、不静默）

| 情况 | 行为 |
|---|---|
| PNG 没有 alpha 通道（白底假透明） | 记 WARN，退回"整图叠图"，**不擅自抠白底** |
| 找不到内部透明区 / 内孔太小 | 记 WARN，退回整图等比缩放（旧路径） |
| 安全内容区过小 | 记 WARN，退回旧路径 |
| 分析异常 | 旧路径仍可用（`build_hole_mask` + 等比缩放） |

### 性能与缓存（实测）

- 4096×2160 相框：降采样到 512×270 分析，**21ms**，几何映射误差 ≤4px
- 1346×719 相框：**8ms**
- 二次启动：**0 次分析**（`相框模型命中缓存`），缓存文件 `~/.cache/omarchy-omaframe/frames/*.json`
- 播放中整机 CPU ≈5%；分析只在**相框加载时**发生一次，绝不在每帧做
- `FrameSlices` 惰性构建一次并在内存里复用（换素材只重算布局，不重新分析）

### 本节的坑（都踩过）

1. **中心片必须用"内孔范围"，不能用"安全内接矩形"**：后者比内孔小 → 相框内会
   露出一圈桌面（透明漏洞，验收项里明确不允许）。安全矩形只用于诊断/兜底。
2. **没有 alpha 通道的 PNG 会让旧的洪泛路径索引越界崩溃**（它无条件读第 4 字节）：
   必须在入口用 `has_alpha()` / `n_channels() >= 4` 挡住，并加回归测试。
3. **安全边距（腐蚀）不能太大**：太大会把可用内孔吃掉；太小则会把羽化/装饰毛刺算进去。
   当前取短边的 1%（下限 2px，在分析分辨率上算）。
4. 相框分析要看**低频几何**：降采样到 512px 精度足够（实测误差 ≤4px），成本从几百毫秒降到二十毫秒。

### 当前限制

- 第一版是 **9-slice**（四角保持 + 四边拉伸）：四边上的连续纹理/花纹会被拉伸；
  装饰若伸进内孔，会在中心片里被拉伸变形（幅度取决于布局）。
  预留了 Mesh Warp 的位置（`FrameSlices` 只需换成 mesh 采样即可），但尚未实现。
- 极端不规则（例如中心片内有大量装饰）时，素材会被装饰盖住一部分（有遮罩兜底，不会漏框）。
- `fit = cover` 保留老行为（按素材比例裁切），供用户主动选择。

## 三十二、引擎修复轮（2026-09-30）

用户报的四个问题 + 修法：

### 1. 相框上出现"绘制的可见线条"（花环最明显）

- **根因**：九宫格每片都用 cairo 填充，而**路径默认开启抗锯齿** → 相邻切片共享的
  那条边被半透明化，于是出现一条发丝细缝（穿过花朵/藤蔓，非常显眼）。
- **修法**：填每一片前 `cr.set_antialias(Antialias::None)`（只影响路径边缘，
  不影响切片图像本身的采样过滤）+ 每片向外 **0.5px overlap**，让相邻片轻微重叠而不是留缝。
  遮罩的九片同理（否则遮罩缝会让媒体透出一条）。

### 2. 不支持 HEIF/HEIC（iPhone 照片）

- **现状**：`gdk-pixbuf` 没有 heif loader（`gdk-pixbuf-query-loaders` 里没有），
  系统里能解 HEIC 的是 **ImageMagick（HEIC delegate）** 和 **ffmpeg**。
- **修法**：`media/mod.rs` 把 `heic/heif/hif` 归为图片；`media/image.rs` 在
  gdk-pixbuf 解不了时（按扩展名或 `ftyp` 魔数判断）调用
  `ffmpeg -i in -frames:v 1 -f image2pipe -vcodec png -` 转 PNG 字节再走原解码流程，
  失败再退回 `magick in png:-`。实测 iPhone HEIC（1081x1441）正常显示。
- **注意**：**不擅自抠白底** —— 没有 alpha 的"假透明 PNG"仍按原样显示并记 WARN。

### 3. iPhone MOV 宽高比错误

- **根因**：手机视频用**容器旋转矩阵**表示朝向：流里 `1920x1080` + `rotation=-90`，
  实际应显示为 `1080x1920` 竖屏。旧代码只读 `width/height` → 得到横屏，
  又把画面缩放进横屏目标框 → 画面被压扁。
- **修法**：`probe_size()` 改用 `ffprobe -of json` 同时读
  `stream_side_data.rotation` 与 `tags.rotate`，在 90/270 时交换宽高；
  ffmpeg 侧显式 `-autorotate 1`（输入前），让画面先转正再缩放到已按旋转后算好的目标尺寸。
  实测：`1920x1080 rotation=270 → 显示 1080x1920`，画面竖屏且不变形。

### 4. 素材要遵守"最大宽度/最大高度"

- **根因**：九宫格让相框可以拉伸后，**相框外框**会超出配置的上限盒
  （实测上限 495x930 的 9:16 素材得到 818x1152 的相框）。
- **修法**：`layout_adaptive()` 增加 `max_frame` 参数：外框超标时**整体等比缩小**
  （素材与边框一起缩，用 `floor` 避免取整溢出），并同时以整块 surface 为上限。
  结果：相框 ≤ 上限、素材 ≤ 上限且比例不变（单测断言）。实测 496x698。

### 复测结论（本轮）

- 34 → **35 个单测通过**（新增"遵守上限"用例），编译 0 warning
- 视觉回归重跑：3 相框 × 4 比例共 12 张（`target/visual/`），
  无细缝、无变形、无穿框、素材铺满、全部在 720 上限内
- HEIC ✓ / MOV 竖屏 ✓ / 缝隙消失 ✓ / 上限遵守 ✓

## 三十三、MOV 被"跳过" + 调试网格被误认成渲染 bug（2026-09-30）

### 1. MOV 视频被跳过（一帧都不播）

- **现象**：日志里 `载入视频 …` 正常、`ffmpeg 启动：1080x1922` 正常，但紧接着
  `视频播放结束（共 0 帧）` → 视频一闪而过，看起来"被跳过"。
- **根因**：上一轮修 iPhone 旋转时，我在 `-i` 前显式加了 `-autorotate 1`。
  但**这个 ffmpeg 构建把 `-autorotate` 当作输出选项** →
  `Option autorotate … cannot be applied to output url 1 … Move this option before the file it belongs to`
  → ffmpeg 直接报错退出 → 0 帧。
- **修法**：**删掉显式 `-autorotate`**（自动旋转本来就是默认开启的，容器有旋转矩阵时
  ffmpeg 会自己插转置滤镜）。顺带把视频目标尺寸取成**偶数**（yuv420p 等格式对奇数敏感）。
- **教训**：交互式 `ffmpeg` 命令改动后，**必须手动跑一遍同样的参数**看真实报错
  （app 里 `-loglevel error` + `stderr(Stdio::null())` 会把原因吞掉，只看到"0 帧"）。

### 2. "十字交叉细线"其实是调试网格

- **现象**：相框上出现十字/井字形细线，观感割裂，像是"计算最大内接矩形时画出来的"。
- **排查**：对**纯色素材（品红）+ 木纹相框**做像素级扫描：
  媒体内部中央区域 0 个异常点、中心横线 0/142、中心竖线的 52 个点全部是
  相框顶部报纸角/底部书本的**合法装饰重叠**（`y` 只在媒体上下边缘附近）。
  → **当前渲染没有任何透明缝线**。
- **真相**：那是我用 `PF_FRAME_DEBUG=1` 起的**开发调试网格**（切片边框 + 内容区虚线框），
  正好是十字/井形；用户的截图/观感来自那个实例。
- **修法（防误判）**：
  1. 环境变量改成必须显式的 `PHOTO_FRAME_DEBUG_OVERLAY=1`（旧名字不再触发）；
  2. 一旦开启会在日志里打 `WARN`，方便把"调试网格"和"真渲染问题"分开；
  3. 测试结束一律**不带任何调试环境变量重启**。
- **验收方法**（可复用）：用纯色素材 + 无内部装饰的相框，扫描媒体矩形中央 15%~85%，
  任何非素材色像素都算异常；再沿中心横/竖线逐像素扫一遍。

### 附：切片发丝缝的修法（本轮之前）

九宫格每片用 cairo 填充时**默认开抗锯齿**，相邻片共享边被半透明化 → 发丝细缝。
修法：填充前 `set_antialias(Antialias::None)` + 每片向外 0.5px overlap（遮罩九片同理）。

## 三十四、播放键居中 + 底图圆角 + 相框十字线根因（2026-09-30）

### 1. 播放/暂停按钮移到**底图正中**，且随缩放动态跟随

- `ControlLayout` 新增"媒体矩形"，`play_rect()` 以**媒体中心**定位（之前固定在相框底部中央）。
- 坑：`geometry()` 在**九宫格路径里提前 return**（`media_rect.set(...)` 在函数末尾）→
  控件拿到的是 (0,0,0,0)，按钮跑到相框左上角。修法：两条 return 路径都写缓存 ✓。
- 坑：`ControlLayout::with_media` 的媒体坐标必须是**相对相框左上角**的偏移；
  只传尺寸、位置传 0 会让按钮算错中心 ✓。
- 缩放/改设置时：媒体矩形每帧由 `geometry()` 重新计算并写入缓存 → 按钮自然跟随 ✓。

### 2. 底图（图片/视频）圆角 —— ⚠️ **本节方案未落地**

> 当前代码里 **搜不到 `corner_radius`**（`FrameConfig` 无此字段，源码零实现）。
> 下面的算法与坑是**设计稿**，不是已验证结论；要启用需先补实现 + 单测。
> （F16 在 [`REQUIREMENTS.md`](REQUIREMENTS.md) 里仍挂验收，当前实际表现是“底图方角”）。

- **可行**，做法：媒体绘制后用 `DestOut` 擦四个角（图片/视频同一套路径，开抗锯齿 → 边缘平滑）。
- 半径默认 **-1 = 跟随相框**：分析时量"内孔每条边第一个透明像素离包围盒边的距离"（中位数），
  多数采样一致才认为是圆角；方角相框得到 0 → 底图不圆 → **不会露出桌面**。
- 配置 `frame.corner_radius`：-1 跟随相框 / 0 关闭 / >0 固定像素（设置页有对应行）。
- 路径写法（踩过两次错）：**每角 = 直角方块(r×r) 减去 四分之一圆**，用 EvenOdd 填充。
  不要用"外框 − 圆角矩形"（那是整圈边框，会把四条边也擦掉 ✗）。
  单测 `corner_cutout_erases_only_the_corners` 锁住这个行为 ✓。

### 3. 相框上的"十字交叉细线"（复古/大头贴可见）

- 根因是**九宫格接缝**：目标矩形用浮点（kl/kr/mw…）计算，光栅化后相邻片之间
  留下 1px 缝；之前用"每片外扩 0.5px overlap"补偿，会把相邻片**放大 1px**，
  接缝处变成一条硬边线（穿花纹更显眼）。
- 修法：`layout_adaptive` 里 9 个目标矩形改为**整数累加**（x0→x1→x2→x3、y0→y1→y2→y3），
  相邻片像拼图一样精确相接；填充用 `set_antialias(None)`，**不再做像素级外扩**。
  遮罩九片使用**完全相同**的矩形 → 擦除边界与绘制边界严格对齐。
- 注意区分：大头贴等相框 PNG **本身**就带细装饰线（对比原图可确认）✓ 那种不是我们的问题。

### 4. 相框库改名后设置静默失效（附带修）

- 现象：相框库被整理成 `横-*` / `竖-*` 两组后，配置里仍是旧名（如 `木纹.png`），
  程序只在日志里 WARN 一句"不存在"，**画面上相框直接消失**，用户容易以为是渲染坏了。
- 修法：`resolve_frame_name()` 做三级回退并把结果**写回配置**：
  ① 原名 + `横-` / `竖-` 前缀；② 去掉已有前缀；③ 库里第一个 PNG。
  命中时记 INFO/WARN 并 `commit()` 一次，用户下次打开就是新名字 ✓。

## 三十五、"十字细线"的四层排查（2026-09-30）

现象：相框开口边缘出现 1px 亮线（透出桌面），四角最明显。逐层排除：

1. **不是九宫格接缝**（几何）：目标矩形早已改成整数累加、精确相接。
2. **不是遮罩**（A/B 实测）：`PF_NO_MASK=1` 跳过遮罩后线依旧。
3. **媒体自身边缘**：`append_texture` 的目标矩形边缘会采到纹理外的透明像素
   → 照片那一圈变半透明。修法：媒体 clip 与目标矩形都向外扩 `MEDIA_EDGE_BLEED`(3px)。
4. **相框内沿半透明斜边**：开口边缘常带抗锯齿/高光，后面没内容就会透出桌面。
   修法：遮罩的**中心片**同样外扩 3px，让媒体多探入几像素、由斜边盖住。
   边片**不能**外扩（那边已是实心框体，外扩会擦掉本该被盖住的媒体）。

关键教训：相框切片与遮罩切片**不能各扩各的**，否则两者边界错位 → 又出现透光线；
`Mask 中心片外扩` 与 `相框切片 1px 重叠` 是两件不同的事，别混。

## 三十七、“十字细线”最终定案（2026-09-30，接三十四-3 / 三十五）

用户报：“四边与四角拼接处不紧密，看起来有十字线割裂”。实测确认**有两个独立成因**，
三十四-3 只写了第一个，第二个此前一直没被定位 —— 而且第一个恰好掩盖了第二个。

### 成因①：绘制时每片外扩 1px（**已修**）

`media_view.rs` 绘制九宫格时给每片加了 1px overlap（注释写“光栅化会取整，0.5px 可能仍留缝”）。
但 `layout_raw` 早已用**整数累加**生成 9 个矩形（x0→x1→x2→x3、y0→y1→y2→y3），
相邻片天然像素级相接，根本不需要补偿。外扩的真实后果：

* 每片从 `dw/sw` 变成 `(dw+1)/sw` —— **被重新缩放**；
* 相邻两片内容来自 PNG 的**不同区域**，重叠 1px = 把 A 片边缘内容盖到 B 片上 → 1px **内容断层**；
* T 型交点（角片 × 边片）处两条断层相交 → 就是那条“十字线”。

**已删掉整段 match 覆盖，九片严格按 `layout.dst` 拼接。**
不留缝靠三件事（缺一不可）：① `layout_raw` 整数累加；
② `set_antialias(Antialias::None)`（否则共享边被半透明化）；
③ translate 到整数原点后 fill 整数矩形，cairo 正好填满 `[d.x, d.x+d.w)`。
**别再为了“保险”加 overlap —— 那正是成因。**

### 成因②：模型内孔比 PNG 真实透明区内缩约 1 个分析像素（**已绕开**）

分析在降采样图（≤512px）上按 alpha 阈值找内孔，紧贴内孔边缘的那一圈分析像素被框体
alpha 稀释、达不到透明阈值 → 映射回原分辨率后内孔**偏内**。
于是 `slices_src` 切出的**每条边片内缘带 1px 透明行**（合成相框实测：
模型 `hole.y=101`，真实透明从 `y=100` 开始，TOP 片 = 行 0..100，行 100 是透明的）。

这 1px 透明行里：**遮罩不擦**（alpha=0）、**相框不盖**（art 透明），
而媒体有 `MEDIA_EDGE_BLEED` 外扩 → 照片从**整条内缘**渗出 1px，
在四角与边片的 T 型交点处连成十字。早期那个 1px overlap 恰好把它盖住了，
所以拆掉 overlap 后②才暴露出来（**这解释了“修了反而出现新线”**）。

**修法（已采用，零风险）**：媒体绘制**严格 clip 在中心片矩形内**（`clip = media_rect`），
物理上不可能越界；边缘**不会半透明**靠的是 `MEDIA_EDGE_BLEED` ——
纹理被缩放到“媒体矩形 ±3px”再被 clip 裁回媒体矩形，clip 边界上的采样点
距纹理自身边缘还有 3px，双线性取到的是纹理内部像素。
两个条件同时满足，就**不需要**外扩边片去盖半透明边，成因①也不会复发。

顺带清掉：遮罩循环里 `let b = 0.0;` 的死代码和与实现不符的注释
（注释声称“中心片外扩 1px”，实际 b=0）。遮罩与相框现在用**完全相同**的矩形。

### 试过但**无效**（别重复）

把 `frame_model` 的 `hole_rect` 向外补 1 个分析像素，想让边片内缘变实心：
**反而更糟**（角点漏边变大）—— 内孔变大后媒体矩形也跟着大，
边片内缘那 1px 透明行在 dst 里被拉得更明显。已回滚，`ANALYSIS_VERSION` 保持 3。
若将来要治根，正确做法是在**原始分辨率**上对内孔边界做一次小范围精确扫描，
而不是在降采样图上估。

### 验收方法（可复用，含四个踩过的坑）

1. 合成一张**纯 2D 渐变**边框 + 硬边内孔的测试 PNG 丢进 `frame/`：
   任何切片边界都表现为渐变断层，零歧义。真实相框自带灯笼/书本/花纹会干扰判读。
2. 相框在 layer **bottom**，终端铺满屏幕时拍不到 → 切空工作区再 grim：
   `hyprctl dispatch 'hl.dsp.focus({workspace=9})'`
   （**Hyprland 0.56 是 Lua 语法**，写 `workspace 9` 会报 `')' expected`）。
3. 切换后等 **≥3s** 再截，否则会拍到过渡态/调光中间值，造成**全屏均匀亮度偏移**，
   diff 全红但与渲染无关（踩过，浪费了一轮）。
4. 对比必须用**固定绝对坐标**裁剪。**不要**用“找品红像素求 bbox”定位接缝：
   Omarchy 壁纸本身含品红，且**相框四角透明**（壁纸会透过来）→ bbox 完全不可信（踩过）。

### 三十八、内孔边界必须在**原图**上精修（2026-09-30，接三十七成因②）

三十七只“绕开”了成因②（媒体严格 clip 在中心片内），**没有治根**：边片内缘那 1px
透明行仍然存在，只是不再有媒体能漏进去。用户复测后确认缝隙仍在，要求“完全对齐不留空隙”。

**治根做法**（`frame_model::refine_hole_edges`，`ANALYSIS_VERSION` 3→4 使旧缓存失效）：
从降采样分析得到的 `hole_rect` 出发，在**原始分辨率**上从内孔中心向四个方向扫描，
沿透明像素一直向外，碰到第一个 `alpha > threshold` 的像素就停；每个方向取多条采样线里
**最外**的那条（避开内孔里的花朵/藤蔓装饰提前挡住）。
只在透明像素上外扩，所以只会更准、不会误判。

精修后 `hole` = 真正的透明/不透明跳变 → `slices_src` 切出的**每条边片内缘都是不透明框体**：
遮罩能擦、相框能盖，缝隙从根上消失。

**回归测试** `refined_hole_makes_every_edge_slice_opaque`（37 个单测之一）：
构造一个内孔边缘带 1px 半透明羽化带（alpha=90 > 阈值 8）的相框 —— 这正是降采样分析
把内孔算小的典型情形 —— 断言精修后内孔四邻**必须是不透明**。
已验证该测试在**去掉精修后会失败**（`上边 片内缘 alpha=0`），是真回归测试而非摆设。

**实测（合成渐变相框 + 纯品红媒体，零歧义）**

| | 媒体矩形上方的像素（y=-1） | 媒体首行（y=0） |
|---|---|---|
| 精修前 | 8 ← **媒体漏在矩形外** | 9（部分混合） |
| 精修后 | 7 ← 纯框体 | 9（干净阶跃） |

`横-木纹.png` 实测：媒体下缘、左缘各有一条细亮线横穿书本装饰 → 精修后消失。
相框尺寸 715x441 → 714x438（内孔取真实透明区，略小 1~3px，属正确变化）。

### 三十九、设置页不再显示相框库路径

`相框样式` 行的副标题原来是 `内置相框库 N 个（/home/sen/Omaframe/frame）`。
`frame_dir()` 的解析顺序是「exe 同级 → exe 上级 → 编译期源码目录」，
所以这个路径在安装版和开发版**不一样**，对用户没有决策价值。改为只显示数量。

**注**：`gdk-pixbuf 0.22` **没有**像素读取 getter，只有 `put_pixel` 和 `unsafe pixels()`；
读原图 alpha 必须 `unsafe { pb.pixels() }` + 手动算 `y*rowstride + x*n_channels + n-1`。

### 四十、九宫格接缝的**真正**根因：每片一个 GSK 渲染节点（2026-09-30）

三十七 / 三十八 修的都不是这条线。用户第三次复测仍报“四角区域有透明十字线、拼接留空隙”，
说明还有第三个成因，而且是**绘制层**的，不是几何层也不是切片层。

#### 排查（按证据逐步排除）

1. 九宫格 9 个 dst 矩形**精确拼图**（插桩 dump 确认：`40..112..661..734` 之类，首尾相接）。
2. 切片 surface 内容**正确**（插桩读 surface 像素：TOP 片 `surf[0,mid]=(57,43,60)`
   与源图 x=100 处一致；末列也一致）。
3. 换 `Filter::Good → Nearest` **无效**（亮线依旧）→ 不是采样过滤。
4. 用合成渐变相框（任何拼接错位都会变成可见断层）复现成功：
   **每条切片边界都有一条 1px 亮线**，横向扫描 `ΔR≈+9~20`。

#### 根因

九片各自调用 `snapshot.append_cairo(&rect)` → 每片是**独立的 GSK 渲染节点**。
节点边界落在**分数设备像素**上（本机缩放 1.6×：逻辑 112 → 设备 179.2），
相邻节点各自做像素对齐、取整方向不同 → 边界处出现 1px 亮线/缝。
**显示器缩放不是整数时必然出现**（1.0 缩放看不出来，所以早期测试没发现）。

#### 修法

**九片画进同一个 cairo 节点**：`frame_rect` 上只 `append_cairo` 一次，
片内用 `save/translate/scale/restore` 定位。遮罩九片同理。
修复后合成相框的边界亮线 **2 处 → 0 处**（四边框带扫描全为 0）。
`横-木纹.png` 实测：边框木纹的**断层消失**（修复前下边框/右边框中段有明显错位跳变）。

**注意**：这个改动会让整个相框 art 按精确浮点位置重绘（实测约 40% 像素变化，
媒体区完全不变），所以**验收必须看成对对比图**，不能只看“有没有报错”。

#### 教训

“接缝有问题”可能在三个不同层：**几何层**（矩形不tiling）、**切片层**（source 切得不对）、
**绘制层**（节点/像素对齐）。前三轮我只查了前两层就下结论，来回三次。
**分层排查要留到最后：几何 → 切片 surface 内容 → 绘制节点**，每一层都要有插桩证据。

### 四十一、缓存键必须包含**所有**分析参数（2026-09-30）

改 `HOLE_SOLID_ALPHA` 后实测**毫无变化**：日志显示 `相框模型命中缓存`，内孔还是旧值。

**原因**：`FrameModel` 的缓存键（`cache_key`）只哈希了
`path + mtime + size + ANALYSIS_VERSION + alpha_threshold`，
**没有包含 `HOLE_SOLID_ALPHA` 这类新增的分析参数** →
改了参数但版本号没动 → 命中旧缓存 → 新逻辑完全不生效。

**教训**：
1. **只要动了任何影响分析的参数/算法，必须同时升 `ANALYSIS_VERSION`**
   （4→5 之后内孔立刻从 `1119x533 @91,81` 变成 `1117x529 @92,83`）。
2. 调试“改了没反应”时，**先看日志有没有 `命中缓存`** —— 这类问题最容易误判成“改动无效”。

### 四十二、相框内缘的软硬是 PNG 自带的（解释了“为什么只有某几条边有缝”）

实测 `横-木纹.png` 内孔四边 alpha 过渡：

| 边 | alpha 过渡 | 宽度 |
|---|---|---|
| 上 | 254 → 253 → 243 → **0** | ~2px（硬） |
| 下 | 0 → 4 → 60 → 206 → 248 → 252 | ~4px（软） |
| 左 | 254 → 236 → 192 → 60 → 16 → 1 | ~6px（软） |

所以**只有软的那几条边**会出现“半透明过渡带”观感 —— 用户报的
“左上已好、左下/右下/右上仍有缝”正好对应这个软硬分布。

**修法**：内孔边界取相框 alpha **接近实心**处（`HOLE_SOLID_ALPHA = 240`），
而不是“刚刚透明”（`alpha_threshold = 8`）。
后者会让边片的**第一行只有 alpha 9~60（几乎透明的框体）**：
既盖不住、又没有媒体，桌面就从这 1px 半透明行透出来 ——
正是用户说的“透明缝隙、可以透出桌面图像”。

**注意**：这条改动让内孔小幅收缩（2~4px，照片略小），
且**视觉改善幅度我用像素度量证明不了**（木纹自身的浅色倒角把度量饱和了），
所以验收必须以**人眼看成对效果图**为准。

## 四十三、播放/暂停按钮消失或只显示一半（2026-09-30）

**现象**：拖动右下角缩放、把展示区缩小后，底图正中的播放/暂停按钮**消失或只显示一半**。

**根因**：九宫格绘制路径里控制层的变换顺序写反了——

```rust
snapshot.save();
snapshot.translate(fx, fy);          // ← 先平移快照
let cr = snapshot.append_cairo(&frame_rect);   // ← 再建节点
```

`append_cairo` 的**裁剪框**取“调用那一刻”的快照变换。先平移再建节点，
裁剪框就变成 **(2fx, 2fy, fw, fh)** —— 控制层被左/上各裁掉 fx/fy 像素。
相框缩小/移位后按钮中心移进被裁区域 → 消失或只剩一半。

**修法**：先建节点（此刻快照只被拖动偏移平移过，裁剪框正好落在相框处），
再平移**上下文**：

```rust
let cr = snapshot.append_cairo(&frame_rect);
cr.translate(fx, fy);
crate::controls::paint(&cr, &layout_ctl, &self.controls);
```

**实测（相框 198x123 @x=600,y=300，`PF_FORCE_HOVER=1` 强制显示控件层）**：

| | 媒体中心 ±24px 内非品红像素 | 按钮 |
|---|---|---|
| 修复前 | **0 / 2304** | 完全消失 |
| 修复后 | **964 / 2304** | 正常 |

**注意与兜底路径的区别**：兜底路径把**绝对坐标**传给 `ControlLayout` 且不额外平移，
所以它是正确的（注释里写“绘制用表面坐标”）。**两条路径坐标系不同，改一条时别照抄另一条。**

**验收手法（可复用）**：
`PF_FORCE_HOVER=1` 环境变量会强制控件层常显（`media_view.rs` 里已有接线），
不用真的把鼠标移过去就能截图验收；配合“媒体中心附近非品红像素计数”判断按钮是否被裁。

## 四十四、相框库压缩的**默认方案**（2026-09-30）

`frame/*.png` 曾经 ~50MB。全量优化后 **~18MB（-65%）**，做法是
`scripts/optimize-frames.py`（已入库，**以后默认采用**）：

1. **等比缩放到最长边 ≤ 1000px**。相框实际渲染在 ~400~700px，1000px 仍有 1.4× 余量。
2. **RGBA 降采样必须「预乘 alpha → 插值 → 去预乘」**。
   直接对 RGBA 做 LANCZOS 是错的：Lanczos 核会取到透明像素里残留的 RGB，
   把不透明区颜色带到透明边 → 桌面上出现彩边/黑边。实测：
   - 朴素 RGBA Lanczos → 透明区 RGB **75 种**（被污染）
   - 预乘→缩放→去预乘 → 透明区 RGB **1 种**（纯 [0,0,0]，干净）
3. **无损重压缩**（Pillow optimize + ImageMagick 各种 filter/strategy，取最小），
   **逐位校验** RGBA 相同、且仅当严格更小才覆盖。

**为什么不用 pngquant/量化**：相框的**内孔/边框是运行时按 alpha 分析出来的**，
量化会改 alpha → 直接改变九宫格几何，违背“保持透明信息”。缩放本身已能把
50MB 降到 18MB，无需有损工具。

**约束与注意**：
- 缩放只改源图，**内孔/边框是重新分析出来的**（不是写死的坐标），所以逻辑安全；
  但改源图后应 `rm -rf ~/.cache/omarchy-omaframe/frames/` 强制重分析。
- 校验项：尺寸 ≤maxdim、RGBA 合法、alpha 覆盖 0~255、透明区 RGB 唯一。

### 四十五、打包相框库的两条硬规则（2026-10-02）

**① frame/ 以本机为唯一事实来源，改完必须先提交再打包。**

`PKGBUILD` 的 `source` 是 **GitHub tag 归档**，不是本地工作区。若 `frame/` 有未提交
的新增/改名，包里仍是旧快照 —— 曾出现安装版还在用 `大头贴-*`、仓库已改成 `方-*`
的错位（`pacman -U` 后设置页列出的相框和用户改的对不上）。

`scripts/check-release.sh`（已挂 pre-push）现在会**硬拦**两种情况：
- `git status --porcelain -- frame` 非空 → 报错并提示先提交；
- HEAD 没有 tag → 警告（source 指向 tag 归档，没 tag 就打不出可下载的包）。

命名约定（程序按前缀分类「横/竖/方」）：`横-*` / `竖-*` / 其余（`方-*`）算方形。

**② 发布版只使用系统通用目录，不带构建机路径。**

`config::frame_dir()` 的候选 7（cargo 开发布局）和 8（`CARGO_MANIFEST_DIR` 编译期源码
目录）依赖**构建机上的源码路径**，是个人路径。已用 `cfg!(debug_assertions)` 限定为
**仅 debug 构建**参与；release/pacman 包只剩：

1. `$OMA_FRAME_DIR`（显式覆盖，开发/排查用）
2. exe 同级 / 上级 `frame/`（便携安装）
3. `<prefix>/share/omaframe/frame`（`make install` / `install.sh` 布局）
4. `/usr/share/omaframe/frame`（系统包布局）
5. `$XDG_DATA_HOME/omaframe/frame`

开发期想让相框指向本仓库（改完重启即生效、不用重打包），用 systemd drop-in 注入
环境变量，而不是编译进包：

    ~/.config/systemd/user/app-omaframe@autostart.service.d/frame-dir.conf
    [Service]
    Environment=OMA_FRAME_DIR=/home/sen/Omaframe/frame
    # 改完 systemctl --user daemon-reload

注意：**手动从终端跑 `omaframe`（不经 systemd）不带这个变量**，会回落到
`/usr/share/omaframe/frame`（打包时的快照）。确认当前用哪个：看日志里
`相框 /…/xxx.png` 的路径，或 `tr '\0' '\n' < /proc/<pid>/environ | grep OMA_FRAME_DIR`。

## 全面审查：同类逻辑/代码错误的排查清单（2026-10-06，v0.5.5）

起因：转场里漏了一个 `snapshot.pop()` 造成"相框闪屏 + 新图瞬间弹出"。这类 bug
**单测覆盖不到、肉眼现象又容易误判**，所以把同类风险做成固定检查项。

### 1. GtkSnapshot 栈：`save/restore` 与 `push_*/pop` 是**同一个栈**，必须严格配对

GTK4 源码里 `gtk_snapshot_save()` 与 `gtk_snapshot_push_*(opacity/clip/transform)`
都往同一个 state 栈压栈；`gtk_snapshot_restore()` 会 `g_return_if_fail(state == SAVE)`，
`gtk_snapshot_pop()` 要求栈顶是 group。**配错对象就静默失效**：
`save()` + `push_opacity()` + `restore()` 的结果是 —— `restore()` 发现栈顶是 group，
断言失败直接返回，**那个 opacity 组永远不闭合**，把之后画的遮罩/相框全吞进去。

所以每改一次绘制代码，必须按**括号配对**逐块核对，而不是看总数是否相等。
当前 `media_view.rs` 的三处（媒体 / 旧图 / 新图）与两条分支（九宫格 / 遮罩回退）均已核对：

| 块 | 开 | 闭 |
|---|---|---|
| 外层（含拖动偏移） | `save` | 分支 return 前 `restore`（九宫格 L546 / 回退 L644） |
| 媒体裁剪 | `save` + `push_clip` | `pop` + `restore` |
| 旧图 | `save` + `push_opacity` | `pop` + `restore` ← **就这里漏过 pop** |
| 新图 | `save` + `push_opacity` (+`push_clip`) | `pop` (+`pop`) + `restore` |

### 2. "绘制矩形随内容变化"时，不能只看当前矩形

`prev_rect` 那个 bug 的一般形式：**一个会随内容变化的几何量，动画却假定它不变**。
- 相框尺寸由素材比例推导 → 换素材时矩形变 → 用新矩形画旧图必然对不齐。
- 结论：转场里凡是"上一张"的几何，都必须**在切换的那一刻存下来**；
  若某个效果要求两张图处于同一坐标系，就**统一铺满同一块矩形**（推动类用的就是这招），
  而不是指望两帧矩形恰好相同。

### 3. 浮点→整数一律 `.round()`，且同一逻辑只允许一套坐标

- `geometry.rs` 已统一 `.round()` ✓；
- 反例（已修）：控件命中检测用 `(mx - fx as i32) as f64` —— 先截断再加回浮点，
  与绘制侧（整数几何）不是同一套坐标，在 1.6x 缩放下按钮"看得到点不到"。
  **修法：全程 f64，最后才 round。**

### 4. 装饰类代码禁止 `expect()`

托盘图标构造里的 `ImageSurface::create(..).expect(..)` 一旦失败（OOM / 后端异常）
会让整个程序 panic —— 而它只是画一个 22x22 的图标。
**修法：`match` 失败 → `warn!` + 返回空 pixmap，让宿主退回 `IconName`。**

### 5. 新增配置字段必须带 serde 默认值（旧配置兼容）

`Config` 及各子结构均已 `#[serde(default)]` ✓，因此旧版 `config.toml`
缺少 `[transition]` 整段也能正常加载，不会报错或丢配置。**新增字段时保持这条。**

### 6. 排查过、确认**没有**问题的项

- RefCell 重复借用（`borrow()` 跨语句持有 + 同 cell `borrow_mut()`）：未发现。
  `hypr.rs` 那处是作用域内借用 + `state`/`state.timer` 两个不同 cell。
- 定时器泄漏：5 处 `timeout_add_local` 均用 `WeakRef` + 代号（gen）识别过期回调，
  结束时 `ControlFlow::Break` ✓
- 配置字符串 match：`frame.fit` / `video.mode` / `effect` 都有 sanitize 兜底 ✓
- `unwrap()`：生产路径仅 `media_view.rs:1150` 的 `tr.unwrap()`，
  受 `tr.is_some()` 守卫 ✓（可读性上建议改 `let Some(..) = tr`）
